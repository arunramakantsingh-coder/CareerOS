## 5. Structural baseline policy

The full live structural inventory must be generated by the validator in the local environment because the database itself is authoritative for current structure.

The inventory should cover:

- schemas
- tables
- columns and data types
- nullable/default metadata
- primary keys
- foreign keys
- unique constraints
- check constraints
- indexes
- enum types
- sequences
- views
- triggers
- Alembic revisions

Do not copy application data into this document.

## 6. Important data-preservation categories

Migration validation must preserve, at minimum:

- user records
- Professional Profile records
- Career Vault employment records
- skills and certifications
- education records
- Persona records
- uploaded document records and metadata
- identity records
- provider configuration records

Row counts for these categories should be captured before and after a migration affecting their tables.

## 7. Update rule

Update this baseline after every intentionally accepted major schema change.

The baseline migration head must always correspond to the validated repository migration head.

Do not manually edit the baseline to hide drift. First reconcile the actual database and migration graph, then update the baseline.

## 8. Known regression case

The September 2026 incident is a permanent regression test case:

```text
legacy 017 identifier
        +
018 profile descendant
        +
current repository renamed 017 identifier
        +
missing intelligence registry
```

The expected behavior is:

1. detect the known legacy identifier;
2. verify the corresponding schema is already present;
3. normalize Alembic bookkeeping only;
4. do not rerun 017 or 018 profile DDL;
5. apply the missing Intelligence registry migration;
6. reach `019_intelligence_registry`;
7. preserve application data.
